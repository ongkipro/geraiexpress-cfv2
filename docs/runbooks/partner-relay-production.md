# Runbook — Partner relay in production (TASK-601, DEC-219, DEC-232, spec 10 §3–7)

Every step below that touches Vultr, Coolify, Cloudflare DNS/WAF or Mengantar is a **production action: the owner
approves each one** before it runs. Nothing here has been executed against production yet.

## 0. Inputs

- Host: Option A of spec 10 §3 — the existing Vultr instance `geraiexpress` (`sgp`, Coolify 4.7.2, IPv6 off, firewall
  group with 80/443 from Cloudflare only). See `~/.config/ai-local/geraiexpress-prod-access.md` (device-local).
- Image: `infra/partner-relay/Dockerfile` (base `node:24-alpine` pinned by digest, non-root `node`, no dependencies).
  Locally built image passed `verify.mjs` 6/6 (`docs/evidence/TASK-601/local-container-verify.txt`).
- Secrets (generated by the owner, never committed): `RELAY_SECRET` (≥ 32 random bytes, hex). Worker secrets:
  `PARTNER_RELAY_URL=https://relay.geraiexpress.com`, `PARTNER_RELAY_SECRET` (= `RELAY_SECRET`),
  `MENGANTAR_PARTNER_SECRET`. `MENGANTAR_PARTNER_ID` is a plain `vars` entry in `wrangler.jsonc` (not a secret; never
  `wrangler secret put` it, or the binding conflicts). The VPS never holds a Mengantar credential.

## 1. Reserved IPv4 (owner, Vultr)

1. Convert the instance's current primary IPv4 to a Reserved IP (Vultr: Network → Reserved IPs → "convert" from the
   instance) so the address survives a rebuild. Check the current price on the Vultr page first.
2. The reserved address must stay the instance's **primary** IPv4 (a secondary address does not change egress).
3. Record the address in `fleet-inventory.md` (device-local) and in `BUILD-LOG.md`.

## 2. Deploy on Coolify (owner approves; agent may run with the Coolify token)

1. New application `partner-relay` from this repository, build pack Dockerfile, base directory `infra/partner-relay`,
   commit pinned to the verified SHA. Domain `https://relay.geraiexpress.com`; port 8080; **no published host ports**.
2. Environment: `RELAY_SECRET`, `MENGANTAR_PARTNER_ORIGIN` (production Partner origin confirmed with Mengantar),
   `PORT=8080`. Leave `RELAY_SECRET_PREVIOUS` empty except during a rotation.
3. Resource limits: memory 128 MB; read-only root filesystem; drop all capabilities; restart `unless-stopped`.
4. Traefik access logs for this router stay default (no headers/bodies).

## 3. DNS and edge (owner, Cloudflare `geraiexpress.com`)

1. `relay` A record → the reserved IPv4, **proxied**; SSL mode Full (strict); Origin CA cert covers `*.geraiexpress.com`.
2. WAF rate-limiting rule on host `relay.geraiexpress.com`: 30 requests/min per IP → block 10 min.
3. Confirm the Worker has **no** route on `*.geraiexpress.com/*` (only explicit hosts), so a Worker `fetch` to `relay.`
   reaches the VPS.

## 4. Mengantar allowlist (owner ↔ Mengantar contact)

Send the reserved IPv4 to the Mengantar contact for the Partner API allowlist (production and sandbox). Wait for the
written confirmation; record it in `BUILD-LOG.md`.

## 5. Verification — spec 10 §6 (all must pass before production onboarding)

| # | Check | Command | Expected |
|---|---|---|---|
| 1 | Egress IP | on the VPS: `docker exec <relay> wget -qO- https://api.ipify.org` | the reserved IPv4 |
| 2 | Auth, allowlist, size | `secrets-env run -- node infra/partner-relay/verify.mjs https://relay.geraiexpress.com` | `RELAY VERIFY PASS (6 checks)` |
| 2b | Origin closed | `curl -sk --max-time 5 https://<reserved IPv4>/healthz` from a non-Cloudflare host | timeout / refused |
| 3 | Sandbox Partner via relay | `secrets-env run -- node infra/partner-relay/verify.mjs <relay URL for a sandbox-origin relay> --partner-sandbox` | `200` + duplicate → `409 relay_duplicate` |
| 4 | Production Partner via relay | same with production secret and `--partner-production` | `200`; the same call sent directly from a Worker → `403 IP_NOT_ALLOWED` |
| 5 | Public API stays direct | none (DEC-232); `IP_NOT_ALLOWED` on a Public API route alerts (`public_api_ip_not_allowed`) | — |
| 6 | No bodies in logs | `docker logs <relay>` after steps 3–4 | only `{relay_id,target,status,ms}` lines |

Then: `pnpm probes --env production` includes `relay-health`; Super Admin `Sistem & Audit › Kesehatan` shows the relay
reachable.

## 6. Operations

- Secret rotation, IP change and disaster procedures: spec 10 §7 (unchanged). Rotation: set `RELAY_SECRET_PREVIOUS`
  = old, `RELAY_SECRET` = new, redeploy relay, update the Worker secret, remove `RELAY_SECRET_PREVIOUS` after 10 min.
- Rollback: redeploy the previous image digest in Coolify; the Worker has no direct-fetch fallback in production
  (spec 10 §4.3), so onboarding pauses (`registration_pending`) while the relay is down; counters keep working.
