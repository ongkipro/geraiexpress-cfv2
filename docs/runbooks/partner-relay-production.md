# Runbook — Partner relay in production (TASK-601, DEC-219, DEC-232, DEC-235, spec 10 §3–7)

Every step below that touches Vultr, Coolify, Cloudflare DNS/WAF or Mengantar is a **production action: the owner
approves each one** before it runs. `BUILD-LOG.md` (2026-11-23) records the relay rolled out on `99ribu-prod` with
`RELAY VERIFY PASS (6 checks)` and `relay-health` passing; `STATUS.md` still lists TASK-601 as awaiting the owner, so
the owner has to close or correct that row.

## 0. Inputs

- Host (DEC-235): the existing Vultr instance **`99ribu-prod`** (`sgp`, Coolify, firewall group with 80/443 from
  Cloudflare only), reached at its Vultr **Reserved IPv4 `149.28.129.53`** — already the host's primary IPv4 and
  already the AutoLaris egress address. The old dedicated `geraiexpress` VPS (`139.180.142.31`) is deleted. Access
  details: `~/.config/ai-local/99ribu-prod-access.md` and `fleet-inventory.md` (device-local).
- Co-hosting rule: the relay is its own Coolify project/application on its own Docker network; it shares no volume,
  environment variable, secret or database with any 99ribu application, and 99ribu's apps are not changed.
- The host has IPv6 enabled. The relay must leave over IPv4 only (Mengantar allowlists `149.28.129.53`): keep the
  container on an IPv4-only network (Coolify's default bridge without IPv6) and prove it in §5 step 1b.
- Image: `infra/partner-relay/Dockerfile` (base `node:24-alpine` pinned by digest, non-root `node`, no dependencies).
  Locally built image passed `verify.mjs` 6/6 (`docs/evidence/TASK-601/local-container-verify.txt`).
- Secrets (generated by the owner, never committed): `RELAY_SECRET` (≥ 32 random bytes, hex). Worker secrets:
  `PARTNER_RELAY_URL=https://relay.geraiexpress.com`, `PARTNER_RELAY_SECRET` (= `RELAY_SECRET`),
  `MENGANTAR_PARTNER_SECRET`. `MENGANTAR_PARTNER_ID` is a plain `vars` entry in `wrangler.jsonc` (not a secret; never
  `wrangler secret put` it, or the binding conflicts). The relay host never holds a Mengantar credential.

## 1. Reserved IPv4 (already in place — verify only)

1. `149.28.129.53` is already a Vultr Reserved IPv4 attached to `99ribu-prod` as its primary address (recorded in
   `fleet-inventory.md`). Nothing to buy or convert.
2. Before go-live, confirm it is still the primary IPv4 (Vultr instance page) — a secondary address would not change
   the egress source. §5 step 1 proves it from inside the container.
3. Do not detach or move it: the AutoLaris allowlist for 99ribu depends on the same address.

## 2. Deploy on Coolify (owner approves; agent may run with the Coolify token)

1. New application `partner-relay` from this repository, build pack Dockerfile, base directory `infra/partner-relay`,
   commit pinned to the verified SHA. Domain `https://relay.geraiexpress.com`; port 8080; **no published host ports**.
2. Environment: `RELAY_SECRET`, `MENGANTAR_PARTNER_ORIGIN` (production: `https://app.mengantar.com` — `api-public.mengantar.com` answers Partner
   routes with a 301 and the relay never follows redirects),
   `PORT=8080`. Leave `RELAY_SECRET_PREVIOUS` empty except during a rotation.
3. Resource limits: memory 128 MB; read-only root filesystem; drop all capabilities; non-root user (`node`);
   restart `unless-stopped`. Own project `geraiexpress-relay`, never inside the `99ribu` project.
4. Traefik access logs for this router stay default (no headers/bodies).

## 3. DNS and edge (owner, Cloudflare `geraiexpress.com`)

1. `relay` A record → `149.28.129.53`, **proxied**; SSL mode Full (strict); install a `geraiexpress.com` Origin CA
   certificate (`*.geraiexpress.com`) in the `99ribu-prod` Traefik dynamic config, next to the 99ribu one (the host
   only has origin certificates for its own zones today).
2. WAF rate-limiting rule on host `relay.geraiexpress.com`: 30 requests/min per IP → block 10 min.
3. Confirm the Worker has **no** route on `*.geraiexpress.com/*` (only explicit hosts), so a Worker `fetch` to `relay.`
   reaches the relay host.

## 4. Mengantar allowlist (owner ↔ Mengantar contact)

Send `149.28.129.53` to the Mengantar contact for the Partner API allowlist (production and sandbox). If the deleted
host's address `139.180.142.31` was ever registered, ask them to remove it once step 4 below passes. Wait for the
written confirmation; record it in `BUILD-LOG.md`.

## 6. Operations

- Secret rotation, IP change and disaster procedures: spec 10 §7 (unchanged). Rotation: set `RELAY_SECRET_PREVIOUS`
  = old, `RELAY_SECRET` = new, redeploy relay, update the Worker secret, remove `RELAY_SECRET_PREVIOUS` after 10 min. Since control `0020` the
  Worker reads relay URL, relay secret, Partner id and Partner secret from D1 `platform_partner_config` first
  (Super Admin `Sistem & Audit › Integrasi Mengantar`) and only then from the Worker var or secret: when an override
  is saved there, rotate the value there, otherwise the Worker-secret update has no effect.
- Rollback: redeploy the previous image digest in Coolify; the Worker has no direct-fetch fallback in production
  (spec 10 §4.3), so onboarding pauses (`registration_pending`) while the relay is down; counters keep working.
