Verdict: REQUEST_CHANGES

> **Safety Net Access Block:** Reading `apps/worker/src/do/gerai-vault/credentials/*` (`credentials/rotation.ts`) was blocked by `CC Safety Net` (`rule: secret.basename.credentials`). Per tool safety rules, no retry or workaround was attempted; Worker-side `rotateSellerKey` / D1 `webhook_routes` update code under `credentials/*` remains unverified from disk, while all DO-side rotation fence and read-back primitives in `apps/worker/src/do/gerai-vault/connection.ts` and `apps/worker/src/do/gerai-vault/index.ts` were audited.

### Findings

1. **[P1] Public API body-stream timeouts/resets and non-JSON `5xx`/`2xx` responses are not marked `ambiguous` (ADR-0004 duplicate-debit hazard)**
   - **Location:** `packages/mengantar-sdk/src/public/transport.ts:25-27`, `packages/mengantar-sdk/src/public/transport.ts:84`, `packages/mengantar-sdk/src/public/transport.ts:89`
   - **Failure scenario:**
     1. `POST /api/public/{API_KEY}/order` (or `POST /order/pay-unpaid`) reaches Mengantar, debits the seller's prepaid balance, and returns HTTP `200` headers, after which `AbortSignal.timeout` or a socket reset aborts `const text = await res.text()` (`transport.ts:84`). Because `res.text()` is outside the `fetch` `try/catch` (`transport.ts:73-83`), a raw `DOMException`/`TypeError` escapes (`err.ambiguous === undefined`, raw English `err.message`).
     2. Alternatively, an upstream Nginx/Cloudflare proxy returns an HTML `502`/`504` page (or truncated `200` JSON). `JSON.parse` runs before `if (!res.ok)` and throws `MengantarError("parse", templ, res.status, ...)` (`transport.ts:89`), for which `MengantarError.ambiguous` (`transport.ts:26`) returns `false` because it only checks `this.kind === "http"`.
     In both cases, DO callers (`apps/worker/src/do/gerai-vault/index.ts:715, 804`) classify the outcome as a clean provider rejection instead of `reconciliation_needed`, skip read-back, release the masking slot, and permit a retry with a new idempotency key — risking duplicate order creation or double `pay-unpaid` balance debits.
   - **Smallest fix:** Move `const text = await res.text()` inside the `try/catch` (`transport.ts:73-83`), and widen `MengantarError.ambiguous` (`transport.ts:26`) to return `true` when `this.kind === "parse"` and `(this.status ?? 0) >= 500 || ((this.status ?? 0) >= 200 && (this.status ?? 0) < 300)`.

2. **[P1] Partner API body-read failure on `2xx` returns `kind: "error"` (`HTTP_200`) instead of `kind: "maybe_sent"`, breaking `regenerate` fence and `register` reconciliation**
   - **Location:** `packages/mengantar-sdk/src/partner/index.ts:109-116`
   - **Failure scenario:** `PartnerClient.regenerate(sellerId)` (or `register`) receives `200 OK` headers after Mengantar has already rotated `apiKey` + `callbackSecret` (or created the seller), then `res.json()` (`partner/index.ts:109`) fails on body-stream timeout or reset and `.catch(() => null)` yields `json = null`. Because `res.status === 200`, lines `114-115` evaluate `false` and line `116` returns `{ kind: "error", status: 200, code: "HTTP_200", message: "" }`. Callers treat `kind: "error"` as a pre-execution refusal: rotation runs `abortKeyRotation` (`apps/worker/src/do/gerai-vault/index.ts:2056-2065`), lifting the fence with the now-revoked old key still active and skipping `api-key` read-back / `secret_mismatch`; registration (`apps/worker/src/onboarding/service.ts:268-280`) refunds the daily quota unit and reverts to `registration_pending` instead of `registration_unknown` + `sellers/list` read-back.
   - **Smallest fix:** Wrap `await res.text()` + `JSON.parse` in a `try/catch`; if reading or parsing fails (or `res.ok` has no boolean `json.success`), return `{ kind: "maybe_sent", reason: timeout ? "timeout" : "network" }`.

3. **[P1] Seller API key redaction gaps on `2xx` envelope failures, invalid-origin URL construction, deep error payloads, and prefixed `routeLabel`**
   - **Location:** `packages/mengantar-sdk/src/public/client.ts:132-137`, `packages/mengantar-sdk/src/public/transport.ts:37, 70, 99`, `apps/worker/src/mengantar/factory.ts:34`
   - **Failure scenario:**
     1. `transport.ts:99` returns unscrubbed `json` on HTTP `200`. When Mengantar responds `200 OK` with `{ success: false, message: "..." }` (failing `z.literal(true)`), `parse()` (`client.ts:135-136`) throws `MengantarError("envelope", ..., body.message)` without calling `scrubKey(body.message, this.opts.apiKey)`. Callers (`apps/worker/src/do/gerai-vault/index.ts:472, 716, 730`) return `err.message.slice(0, 200)` across RPC/HTTP, leaking any echoed `/api/public/<API_KEY>/...` or raw key in `body.message` (as well as raw English provider text, violating `AGENTS.md §2, §3.5`).
     2. `transport.ts:70` substitutes `encodeURIComponent(opts.apiKey)` into the URL string *before* calling `new URL(...)` outside `try/catch`; a malformed `opts.origin` (e.g. missing scheme) throws `TypeError: Invalid URL` containing the full unredacted URL in `err.message` / `err.input`.
     3. `scrubDeep` (`transport.ts:37`) returns objects at `depth > 6` untouched inside `MengantarError.body`.
     4. `routeLabel` (`factory.ts:34`) uses `^\/api\/public\/[^/]+`; if `MENGANTAR_PUBLIC_ORIGIN` ever carries a path prefix (e.g. `/v1`), `.replace(...)` fails to match and writes `/v1/api/public/<API_KEY>/...` into telemetry logs, D1 `public_api_events.route`, and alert text (`factory.ts:48-56`).
   - **Smallest fix:** Scrub `body.message` with `scrubKey(..., this.opts.apiKey)` (or use a fixed Bahasa Indonesia message) in `client.ts:136`; validate `new URL(opts.origin)` before substituting `KEY_PLACEHOLDER` in `transport.ts:70`; return `"[REDACTED]"` when `depth > 6` in `transport.ts:37`; and change `factory.ts:34` to `.replace(/^.*\/api\/public\/[^/]+/, "")`.

4. **[P1] Crash or DO failure after `approveApplication`'s D1 batch permanently wedges tenant onboarding**
   - **Location:** `apps/worker/src/onboarding/service.ts:186-206`, `apps/worker/src/admin/gerai/routes.ts:183-195`
   - **Failure scenario:** `approveApplication` commits `tenant_applications.state = 'approved'` and `tenants.status = 'active'` in `env.DB.batch` (`service.ts:186-198`) without inserting a `tenant_onboarding` row. It then runs `vault.migrate`, `vault.upsertDefaultOutlet`, and `provisionSeller` outside the batch (`service.ts:201-206`). If the Worker dies after the batch or `vault.migrate` throws `500 TENANT_MIGRATION_FAILED` (*"Coba lagi dari halaman gerai"*):
     1. Re-running `approveApplication` throws `409 APPLICATION_NOT_PENDING` (`service.ts:174`).
     2. `POST /gerai/:slug/onboarding/retry` (`gerai/routes.ts:183`) inner-joins `JOIN tenant_onboarding o ON o.tenant_id = t.id`, matches 0 rows, and fails with `404 TENANT_NOT_FOUND`.
     3. Even with a `tenant_onboarding` row, `provisionSeller` (`service.ts:249`) calls `vault.recordOnboarding` without first running idempotent `vault.migrate` + `vault.upsertDefaultOutlet`, failing forever with `500 TENANT_NOT_READY`.
   - **Smallest fix:** Insert the initial `tenant_onboarding` (`registration_pending`) row inside `approveApplication`'s D1 batch (`service.ts:186-198`), and run idempotent `vault.migrate(tenantId)` + `vault.upsertDefaultOutlet(...)` in `provisionSeller` (or `onboarding/retry`) before `vault.recordOnboarding`.

5. **[P1] `reconcileRegistration` binds `sellers[0]` without checking `externalUserId === tenantId`, ignores DO `VaultResult`, and allows keyless `"connected"` state**
   - **Location:** `apps/worker/src/onboarding/service.ts:296-312`
   - **Failure scenario:**
     1. Line `298` takes `const seller = listed.data.sellers[0]` without verifying `seller.externalUserId === tenantId`. If Mengantar's `sellers/list` filter ever performs prefix/substring matching or ignores an unexpected filter shape, `reconcileRegistration` calls `client.apiKey(seller.sellerId)` (`service.ts:305`) and stores **another tenant's** Mengantar seller ID and API key into `tenantId`'s `GeraiVaultDO` (R4 cross-tenant account hijack).
     2. Line `310` records `"connected"` without checking `if (!key.data.apiKey)` (unlike `provisionSeller` at `service.ts:261-267` which routes empty/null keys to `provider_restricted` / `API_KEY_DISABLED`), allowing `"connected"` with `encrypted_api_key = NULL`.
     3. Lines `301` and `310` ignore the `{ ok: false, refused }` return value of `vault.recordOnboarding(...)` and still update D1 `mirror(..., "connected", ...)`, desynchronizing D1 from an unready DO; line `307` also updates D1 `seller_id` without recording `sellerId` in the DO when `client.apiKey` fails.
   - **Smallest fix:** Match `listed.data.sellers.find((s) => s.externalUserId === tenantId)`; guard `!key.data.apiKey` -> `provider_restricted` (`API_KEY_DISABLED`); record `sellerId` in the DO on `key.kind !== "ok"`; and assert `r.ok` on `vault.recordOnboarding`.

6. **[P2] `PartnerQuotaDO` 60/min limit bypassed on `list`/`apiKey` calls, and daily quota / onboarding state inverted on `KEY_PROVISIONING_FAILED` vs `relay_refused`**
   - **Location:** `apps/worker/src/mengantar/factory.ts:8-19`, `apps/worker/src/onboarding/service.ts:269, 274-277, 282-285, 296, 305`, `apps/worker/src/do/gerai-vault/index.ts:2150`
   - **Failure scenario:**
     1. `PartnerQuotaDO.reserve("call", ...)` (`apps/worker/src/do/partner-quota/index.ts:21`) is never called before `client.list` or `client.apiKey` in `reconcileRegistration` (`service.ts:296, 305`) or `GeraiVaultDO.resolveKeyRotation` (`do/gerai-vault/index.ts:2150`). Concurrent DO `key_rotation_check` alarms and admin reconciliations bypass the global 60 req/min partner cap (`spec 10 §4.2 item 4`) and hit Mengantar `429` limits.
     2. In `provisionSeller`, `releaseRegistration(input.now)` (`service.ts:269`) runs on `KEY_PROVISIONING_FAILED` (`service.ts:274`), refunding a daily registration unit even though Mengantar **already created** the seller (HTTP 500 post-creation, `partner/index.ts:115`). Conversely, on `out.kind === "relay_refused"` (`service.ts:282-284`) — where the relay refused *before* calling Mengantar (`partner/index.ts:36`) — `provisionSeller` never calls `releaseRegistration` (burning a daily unit) and sets `registration_unknown` instead of keeping `registration_pending` per `spec 10 §4.3` (forcing two admin retries to register).
   - **Smallest fix:** Reserve `quotaFor(env).reserve("call", now)` before `list`/`apiKey` calls; only call `releaseRegistration` when `out.code !== "KEY_PROVISIONING_FAILED"`; and handle `out.kind === "relay_refused"` by calling `releaseRegistration(input.now)` and recording `registration_pending`.

7. **[P2] `completeKeyRotation` throws across DO RPC on race, omits `armOutbox()` and 1-hour `status_poll` floor on `secret_mismatch`, and drops `callbackSecret` when `webhook_path_token` is `null`**
   - **Location:** `apps/worker/src/do/gerai-vault/index.ts:2118-2139`, `apps/worker/src/do/gerai-vault/index.ts:2565-2566`
   - **Failure scenario:**
     1. `completeKeyRotation` yields on `await encryptString`/`decryptString` (`index.ts:2108-2110`); if a concurrent `key_rotation_check` alarm finishes `resolveKeyRotation` first, line `2118` throws an uncaught `new Error("STALE_KEY_VERSION")` across RPC instead of returning `{ ok: false, refused: "STALE_KEY_VERSION" }`.
     2. When `completeKeyRotation` moves `webhook_state` from `'active'` to `'awaiting_seller_setup'` (`index.ts:2123`) or `'secret_mismatch'` (`index.ts:2132`, read-back path where all incoming webhooks now fail `BAD_SIGNATURE`), `status_poll` remains at `now + 24h` (`POLL_INTERVAL_ACTIVE_MS`) instead of pulling back to `now + 1h` (`POLL_INTERVAL_INACTIVE_MS`, `PR-02b`), and `completeKeyRotation` returns (`index.ts:2138`) without calling `await this.armOutbox()` / `armAlarm()`. In `sweepInbox` (`index.ts:2566`), `DELETE FROM vault_timers WHERE name = 'inbox_sweep'` also cancels the 24h cleanup of `previous_webhook_path_token` whenever `webhook_inbox` is empty during an earlier sweep.
     3. Line `2119` (`if (encSecret && row.webhook_path_token)`) discards `encSecret` whenever `row.webhook_path_token` is `null`, permanently losing the rotated `callbackSecret` that `sellers/api-key` cannot return later (`spec 10 §4.2`).
   - **Smallest fix:** Return `{ ok: false, refused: "STALE_KEY_VERSION" }` instead of throwing at `index.ts:2118`; pull `status_poll` to `now + POLL_INTERVAL_INACTIVE_MS` when `webhook_state` leaves `'active'` (if `pollCandidates(sql, 1).length > 0`) and `await this.armOutbox()` before returning; keep `inbox_sweep` scheduled at `previous_token_expires_at` while unexpired; and allocate `newPathToken()` + save `encSecret` when `encSecret && !row.webhook_path_token`.

8. **[P2] `connectByok` sets `external_user_id = tenantId` (violating ADR-0003), retains stale `seller_id` in D1, and ignores `rotation_state` fence**
   - **Location:** `apps/worker/src/onboarding/service.ts:316-329`, `apps/worker/src/do/gerai-vault/index.ts:296-322`
   - **Failure scenario:** `ADR-0003` Decision 1 requires `external_user_id` to remain `NULL` on `PR-02` BYOK fallback so BYOK outlets are excluded from Partner `sellers/list` reconciliation. `connectByok` passes `externalUserId: tenantId` (`service.ts:321`) and binds `external_user_id = ?1` (`service.ts:325`), fails to clear `seller_id = NULL, external_user_id = NULL` on `ON CONFLICT(tenant_id) DO UPDATE` (`service.ts:326`), and neither `connectByok` nor `recordOnboarding` refuses calls while `rotation_state !== "idle"` or when already Partner-`connected` — allowing BYOK to overwrite an in-flight Partner rotation while leaving `rotation_state` fenced until `resolveKeyRotation` clobbers it back.
   - **Smallest fix:** Refuse `connectByok` / `recordOnboarding` when `rotation_state !== "idle"` or `onboarding_state === "connected"`, set `externalUserId: null, sellerId: null` in DO, and set `seller_id = NULL, external_user_id = NULL` in D1 `tenant_onboarding`.

9. **[P2] Same-millisecond duplicate `approveApplication`/`rejectApplication` commits duplicate `email_outbox` & `audit_logs` rows; `submitApplication` re-submit lacks state guard**
   - **Location:** `apps/worker/src/onboarding/service.ts:122-128, 177-199, 215-230`
   - **Failure scenario:** `thisCall` guards batch side effects with `decided_at = input.now AND decided_by = input.actorId` (`service.ts:177, 215`). Because Workers freezes `Date.now()` between I/O ticks, two concurrent requests by the same `actorId` sharing `now` will see the second batch's `UPDATE tenant_applications ... WHERE state = 'submitted'` match `0` rows while subsequent statements in the same `DB.batch` still match `decided_at = now AND decided_by = actorId` from the first request — committing a second `application_status` email (`TASK-203` invariant: exactly one email per transition), a second audit row, and an extra `routing_version + 1` before throwing `409`. Additionally, `submitApplication`'s re-submit `UPDATE` (`service.ts:123-127`) has no `AND state = 'rejected'` clause, allowing a race to overwrite a newly decided application.
   - **Smallest fix:** Use a deterministic `email_outbox.id` per submission (e.g. `app-decision:${a.id}:${a.submitted_at}` with `ON CONFLICT(id) DO NOTHING`) or guard `thisCall` with a per-call nonce / prior `updated_at`, and add `AND state = 'rejected'` (checking `changes === 1`) to the re-submit `UPDATE`s.

10. **[P3] `PartnerQuotaDO` never prunes `d:YYYY-MM-DD` buckets despite inline comment**
    - **Location:** `apps/worker/src/do/partner-quota/index.ts:35-36`
    - **Failure scenario:** Line `35` states day buckets older than 3 days are dropped, but line `36` only deletes `bucket LIKE 'm:%'`, accumulating `d:%` rows indefinitely.
    - **Smallest fix:** Extend the `DELETE` predicate with `OR (bucket LIKE 'd:%' AND substr(bucket, 3) < ?)` bound to `wibDay(nowMs - 3 * 86_400_000)`.

### Verified Invariants
- **Public API schema & timeout discipline (`packages/mengantar-sdk/src/public/client.ts`, `transport.ts`):** Every call enforces `AbortSignal.timeout` (15 s default); responses are Zod-validated with `.passthrough()`; 4xx/5xx `MengantarError` paths always use templated `/api/public/{API_KEY}/...`.
- **Partner signature & relay envelope (`packages/mengantar-sdk/src/partner/index.ts:22-29, 86-105`, `factory.ts:10`):** Exact-byte `JSON.stringify` payload signed once with `SHA256(METHOD:PATH::BODY:TIMESTAMP:PARTNER_SECRET)`; relay envelope signs `HMAC-SHA256(RELAY_SECRET, ts + "\n" + id + "\n" + target + "\n" + sha256Hex(body))` with `redirect: "manual"`; production enforces `PARTNER_TRANSPORT=relay` with no direct fallback; `409 relay_duplicate` and `relay_upstream_timeout` map to `maybe_sent`; `regenerate` is never auto-retried.
- **`PartnerQuotaDO` atomic reservation math (`apps/worker/src/do/partner-quota/index.ts:21-38`):** Single `"global"` DO serializes checks inside `transactionSync`; rejected reservations consume neither minute (`60/min`) nor WIB-midnight day (`1000/day`, UTC+7) counters.
- **DO key rotation fence & 24h webhook window (`apps/worker/src/do/gerai-vault/index.ts:328-333, 720, 2038-2166, 2465-2472`, `connection.ts:36-59`):** `key_version` increments and `rotation_state` becomes `'in_flight'` *before* `regenerate`; `sellerKey()` / `keyForDispatch()` block dispatches while `rotation_state !== 'idle'`; in-flight dispatches started under an older `key_version` degrade to `ambiguous` read-back (`index.ts:720`); `resolveKeyRotation` reads back exclusively via `sellers/api-key` (never `regenerate`); `ConnectionView` never exposes key/secret material; previous webhook token + secret verify for 24h.
